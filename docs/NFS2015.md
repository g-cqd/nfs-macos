# Need for Speed (2015) on macOS: what was wrong and what fixed it

**Status:** the game starts, renders, and reaches its menus and controller-layout screen under
Wine on Apple silicon. The user reports it as playable. This document is the record of how that
was reached, written so nobody has to rediscover any of it.

**What this app is not:** the Import edition contains no game data and no part of EA's software;
the game and the EA app are the user's own installation, licensed to the user, run where they
already are. The Bundled edition (§13) carries the user's own, unmodified game files; the
complete portable edition (§15) also carries EA's own client, exactly as EA's official installer
installs it and without any account, session or machine record. No part of this work
emulates, stubs or forges EA services, tokens, activation or licence data, and nothing patches or
unpacks the game or its protection. That was a constraint throughout, not a conclusion.

**How to read the evidence labels.** Every claim below is marked **[verified]** when it was
measured on this machine, or **[inferred]** when it is a reasoned conclusion from measurements
that do not strictly prove it. The distinction is load-bearing: two renderer decisions were
reversed on this project because something plausible was treated as settled.

## 1. The symptom chain

| Stage | Symptom | Resolved by |
|---|---|---|
| 1 | Launched from the EA app, `NFS16.exe` ran 28–36 s, self-terminated, and was relaunched; six generations in a 180 s window, never a window on screen | §3.2 |
| 1a | Launched with no EA process running, it exited `170` and spawned `Core/ActivationUI.exe` plus `EALauncher.exe` with an **empty** `authCode` | §3.1 — not a bug; the client is a hard dependency |
| 2 | Each generation suspended a worker thread, wrote `dr0`/`dr7`, resumed, and then never received the trap it was waiting for | §3.2 |
| 3 | With the trap delivered, the respawn loop stopped entirely — then the process died at ~2:52 with `c0000005` | §3.3 |
| 4 | Rendering worked, but full screen came up at the wrong resolution until windowed mode was toggled by hand | §3.4 |
| 5 | A connected DualShock 4 was not seen by the game at all | §3.5 |

The two self-termination exit codes came from inside the game's own code, not from a Wine fault:
`TerminateProcess` call sites at RVA `0x04bdf5a6` (exit `-6`) and `0x075ca521` (exit `-5`).
**[verified]** — process-exit trace.

## 2. What was ruled out early

Worth recording, because both were plausible and neither was the cause:

- **The x87 sidecar and mtld3d were exonerated** by code-path analysis with file and line
  citations: neither sits on a path that could produce this failure. **[verified]**
- **The network was not a Wine fault.** EA's own session-token invalidation explained the offline
  behaviour; a minimal WinHTTP probe returned the same HTTPS status under both runtimes.

## 3. Root causes

### 3.1 The game cannot start without the EA client

`NFS16.exe` imports exactly one thing: ordinal 100 from `Core/Activation64.dll`. Its `.rdata`
section is 92 MiB at entropy 8.0. **[verified]** — static PE analysis. Its strings include an
Origin/EA SDK authorisation-code flow (`OriginRequestAuthCode entered`,
`PresenceGetAuthCodeRequestParameters`, `AuthCodeClientId`). **[verified]**

With no EA process running, the executable exits `170` and asks for an EA relaunch carrying an
empty `authCode`. **[verified]** — `logs/r01-default.log`, `r02-with-ea.log`, `r03-watch.log`,
`r04-seh.log`.

A single-stub import into a high-entropy container, combined with the breakpoint mechanism in
§3.2, is the signature of a commercial protection wrapper. It is **Denuvo, identified from the
shipping binary's own PDB name**: `NFS16.exe` contains the literal string
`Race.Main_Win64_retail_denuvo.pdb`, alongside the unprotected
`Race.Main_Win64_retail.pdb` and the build path
`C:\monkey\Genesis.GamePatchPC.Win64.Retail\TnT\Local\Bin\`. **[verified]** — `strings` on
the installed executable. That is EA's own build naming for the protected variant rather than
the protection vendor's marker, which is why the precise claim is "identified from the shipping
binary's PDB name" and not "confirmed by a vendor signature". The identification does not change
the fix; the behaviour does.

**Consequence for the design:** the EA app is a dependency to be satisfied, not worked around.
The user installs it and signs in; the app launches it and asks it to start the game.

### 3.2 The protection arms a hardware execution breakpoint that Wine never delivered

Each generation suspended a worker thread, wrote `dr0 = 0x14547de70` and `dr7 = 0x00000001` via
`set_thread_context`, had the write accepted, and resumed the thread. `dr6` then read
`0x00000000` in **all 290 observed samples** — the breakpoint never fired and no
`EXCEPTION_SINGLE_STEP` was ever delivered. **[verified]** — `evidence/wine/trace_debugregs.txt`.

Why, precisely:

- `wineserver` refuses debug registers for translated processes, in `server/mach.c` behind an
  `is_rosetta()` guard. The write path returns `STATUS_UNSUCCESSFUL`; the read path zeroes
  `context->debug`. This is **upstream Wine behaviour, present verbatim in clean Wine 11.18**,
  not a CrossOver addition. **[verified]**
- `is_rosetta()` tests `proc_translated` of **wineserver itself**, which is always a Mach-O
  x86_64 binary, so the guard is permanently true for every thread. **[verified]**
- CrossOver's only patch here ("CW HACK 22131", `dlls/ntdll/unix/signal_x86_64.c`) turns a
  *self*-write failure into a fake `STATUS_SUCCESS` and caches `dr0`–`dr7` — which is why the
  trace shows `NtSetContextThread ... not supported under Rosetta, faking success`. It is
  incomplete: `NtGetContextThread` forces `self = FALSE`, reads the server's zeros, and
  overwrites the cache. Observed 17 times. **[verified]** — `evidence/wine/signal_x86_64.diff`.
- For the **cross-thread** write the protection actually uses, `set_thread_context` replies
  `STATUS_SUCCESS` without calling Mach at all; the real failure surfaces later in the victim
  thread's `select` reply and is silently discarded. Nobody is ever told. **[verified]**

**The fix** is to deliver the breakpoint by emulating the x86 trap flag — single-stepping while a
breakpoint is armed and synthesising the exception at the right address. Four patches, §4.

**Causally established**, by a controlled before/after test on the same prefix, runtime and
launch URI with only `WINE_TF_EMULATION` toggled: with it off, the respawn loop; with it on, the
loop stops completely, zero trap-flag stops, the process runs past 3m50s at about 30% CPU with a
live window. **[verified]**, and reproduced independently on the production CX 11.0 runtime.

Two sub-bugs were found and fixed inside the emulator itself, which is why the first attempts
still failed:

1. A fixed five-second diagnostic cap stopped the emulation rather than the game. Replaced with
   the configurable `WINE_TF_MAX_STEPS` and `WINE_TF_MAX_NS` budgets (defaults were 250000 and
   5 s). **[verified]**
2. Prefixed forms of `PUSHF`/`POPF` were not decoded, killing the process at about 25 s with
   `TFEMU STOP prefixed-flag-instruction-unsupported`. **[verified]**

A regression fixture covers this: **10 checks, 2 failures with the gate off, 0 with it on.**
**[verified]**

### 3.3 D3DMetal cannot render this game; dxmt can

With the protection cleared, the game got as far as rendering and then died at about 2:52 with
`c0000005`, a wild-pointer read at `NFS16.exe` RVA `0x341FB95`, immediately after this log line
(quoted verbatim from `logs/prod-ab.log`):

```
[D3DMetal:LOG:FD43B][UmplementedTimestampQuery_block_invoke:200] Unsupported: D3D11 timestamp query
```

Frostbite uses GPU timestamp queries. The same log also shows
`IDXGIResource::GetSharedHandle` returning `0x80004001` (not implemented). **[verified]** — the
crash, the address, the timing and the log line.

**That the unsupported query *causes* the fault is [inferred], not proven.** The RVA was not
disassembled and sits inside the protected image. The source's own words: *"Strong inference, not
proof."*

What is not inferred is the choice. Switching the DXGI backend for `NFS16.exe` to **dxmt**, a
Metal-backed Direct3D 11 implementation, produced: no fault at that address, 3.4 MB of compiled
Metal shaders in the dxmt cache, `lsof` confirming `dxmt/x86_64-windows/d3d11.dll` as the mapped
library, full screen at 2560×1600, and the title and controller-layout screens. **[verified]**

**The EA client runs on dxmt too, and better.** Measured afterwards on the same prefix and
runtime with only the client's rule changed: the client came up in 30 s and rendered its full
Home interface — sidebar, store banner, artwork, avatar, the game listed under Installed, signed
in — with **zero** ANGLE shared-handle errors, where D3DMetal logged 4 to 10 of
`Could not get offscreen texture shared handle` per session. Those failures are what repeatedly
dropped the EA session and killed the game earlier. **[verified]** So dxmt is not merely
acceptable for the client; it is better than the backend it replaces, and **nothing in this
recipe selects D3DMetal any more.** Resident memory grew from 128 MB to 1053 MB during
startup, sampled live with `ps -Ao pid,etime,%cpu,rss,comm` rather than recorded in any log, so
it is a process observation and no file in this tree carries it.

dxmt was present in the runtime the entire time. It had been tried once, long before, and
produced no window — but that was before the protection could be cleared at all, so the result
said nothing about the renderer. Re-measuring it cost one run and avoided building a second
runtime. **The lesson is in §6.**

### 3.4 First-launch resolution

The game's own options were already correct (`FullscreenEnabled 1`, `2560×1600`, `60`), yet full
screen came up wrong until windowed mode was toggled by hand to force a re-query.
`HKCU\Software\Wine\Mac Driver` in the prefix held only `AllowSetGamma` — no `RetinaMode`.
**[verified]** — read directly from the prefix's `user.reg`.

Setting `RetinaMode` fixes it: with it set, full screen came up at 2560×1600 matching the game's
own file on the first launch. **[verified]** The explanation — that without it the Mac driver
advertises the scaled logical desktop, so the mode the game asks for does not exist and Wine
substitutes the nearest — is **[inferred]** from the setting's documented purpose.

Note the existing bundles disagree on this value: the CoD4 defaults set `Y`, the Most Wanted
defaults set `N`. It is therefore per-recipe configuration, not a shared default. Wine accepts
`y`, `Y`, `t`, `T` or `1`.

### 3.5 Controller

This game reads XInput and has no DirectInput path. Wine's bus driver only marks Xbox vendor
products as gamepads, so a Sony pad reached through the host HID layer never binds to XInput and
the game sees nothing. Setting `Hidraw` to `0` for the device keeps Wine's SDL-backed,
Xbox-mapped device instead.

Verified with a DualShock 4 (VID `054c`, PID `05c4`) at XInput slot 0 across `xinput1_1` through
`xinput1_4` and `xinput9_1_0`. **[verified]** — `controller/padtest-run2.log`.

Xbox button glyphs appear in-game. That is expected: XInput only models Xbox pads.

## 4. The runtime

Built from `https://github.com/athei/wine`, branch `cx-26-patched`, commit **`1a7b0c76`**
(*"ntdll, win32u: Let compatdb.so set the process DPI awareness."*), reporting `wine-11.0`, plus
four patches, exported into `Packaging/NFS2015Runtime/patches/`:

| Patch | Commit | Purpose |
|---|---|---|
| 0001 | `b69c5ca` | Rosetta debug-register state, and trap-flag-based execution-breakpoint delivery — §3.2 |
| 0002 | `2400584` | Configurable `WINE_TF_MAX_STEPS`/`WINE_TF_MAX_NS` budgets instead of a fixed 5 s cap |
| 0003 | `d7c4a19` | Decode instruction prefixes on `PUSHF`/`POPF` |
| 0004 | `52582b2` | The execution-breakpoint regression fixture |

Configure flags, the rebuild procedure and the third-party component manifest (dxmt v0.80 from
`3Shain/dxmt`, Apple GPTK 4.0 beta 2, mtld3d v0.7.0) are in
[`Packaging/NFS2015Runtime/BUILD.md`](../Packaging/NFS2015Runtime/BUILD.md). `--without-vulkan`
is deliberate: nothing Vulkan, MoltenVK or DXVK is built or shipped.

**Toolchain parity gap, carried deliberately.** The build script selects llvm-mingw, but the
delivered `lib/wine/x86_64-windows/ntdll.dll` reports `GCC: (GNU) 16.1.0` — Homebrew's mingw-w64
GCC. **[verified]** by reading the shipped binary. The decision was not to rebuild, so the
runtime that ships is the one that was tested. Consequence: these PE builtins are not
bit-comparable with a CI build, and any future compiler-looking bug should be re-checked against
an llvm-mingw build before being reported upstream.

Licence position is in
[`Packaging/NFS2015Runtime/NOTICE.md`](../Packaging/NFS2015Runtime/NOTICE.md).

## 7. How the app is built: the Import edition

This game cannot use the packager's normal model, which copies verified game bytes into a private
generation inside a prefix the app owns. The account session, the client's registry state and the
machine activation all live in **one** prefix, and duplicating a signed-in prefix invalidates the
session. So:

- `GameKind.nfs2015.copiesGameData` is `false`. `GameInstaller` refuses to publish a generation
  for this game at all, and `BundleManifest` accepts an empty inventory only for a manifest that
  declares `referencesInstallation`.
- The app records which Windows folder the user chose and runs it in place. It copies nothing out
  of it. (The Bundled edition, §13, does not use this: it creates one prefix of its own and seeds
  it once; it never copies a prefix that already holds a session.)
- Two consequences, both deliberate. **Guest drive isolation does not apply** — restricting a
  prefix the app does not own would damage the user's installation. And an app update **cannot
  re-verify game bytes**, because there is no per-file inventory; the recognition rules in the
  manifest are checked instead.
- Settings are read from and written to the game's own
  `Documents/Need For Speed/settings/PROFILEOPTIONS_profile` and nowhere else, so a change the
  user makes in the game's Video menu is what the app shows, and the app can never overwrite it
  with a stale cache. The binary `PROFILEOPTIONS` blob beside it is never touched.
- The one file the app changes outside its own folder is that options file, and only through the
  rules in §16: validated layout, game closed, file unchanged since it was read, backups first,
  atomic replace, read back. The previous bytes are also journalled inside the app's folder, so an
  interrupted edit is replayed before anything reads the file.
- Registry values the game needs are checked against the prefix's own hives and imported only
  when missing, so a prepared prefix starts no Wine process and is left untouched.

Design details are in [`NFS2015-RECIPE.md`](NFS2015-RECIPE.md).

### The x87 sidecar stays in the bundle, and is not optional

It was asked whether this recipe should drop the x87 sidecar, since the game plainly does not
use it. The answer is no, and the reasoning matters because the sidecar is a **shared** pinned
input across every bundle this packager produces.

The game does not need it: `NFS16.exe` is `PE32+ x86-64` **[verified]**, the runtime re-executes
only 32-bit processes through the sidecar, and `ROSETTA_X87_PATH` was unset for every run on the
night the game first worked, including the successful one. That is good evidence about the game.

It is not evidence about the bundle, because the bundle runs more than the game. EA's own helpers
are 32-bit:

| Program | Architecture |
|---|---|
| `EA Desktop/compatibility32/EADesktop.exe` | `PE32 Intel 80386` **[verified]** |
| `Need for Speed/Core/ActivationUI.exe` | `PE32 Intel 80386` **[verified]** |
| `EA Desktop/EADesktop.exe` | `PE32+ x86-64` |
| `NFS16.exe` | `PE32+ x86-64` |

`compatibility32/EADesktop.exe` was observed **running** during a live session, and
`ActivationUI.exe` is the process the game spawns when activation is needed — §3.1. Those are
exactly the processes the sidecar exists for. They ran without it on this machine, but "works
without it here" and "should ship without it" are different claims, and dropping a shared pinned
input from one recipe would let that recipe's runtime diverge from the others for the sake of one
543 KB binary. So it stays, and `verify_inputs` keeps requiring it for every recipe.

**The pin was not stale, only missing.** The build directory holding the artifact was deleted
during a disk cleanup, which is what produced `Missing or linked pinned artifact: x87sidecar`.
Rebuilding from a scratch clone at the pinned revision `8aa4d30` with the project's own CMake
release build produced
`cbc236c4dfc78fa466a52f1a7cc322f6733d44ceebe02ac493314a8fffdb2291` — **byte-for-byte the hash
already recorded in `runtime-inputs.json`** **[verified]**. `x87sidecar --probe` reports
`supported` and exits 0. No pin changed, and the CoD4, Most Wanted and Far Cry 2 recipes need no
update either, because they share that same unchanged pin.

That reproducibility is worth keeping: the artifact can be regenerated from source at a named
revision rather than depending on one surviving build directory. It was confirmed a second time
when the pin moved to `12afdc2`: a scratch clone at `8aa4d30` in a *different* directory produced
the same hash again, so the build does not depend on where the clone sits, and the build at
`12afdc2` is byte-identical to it (`cmp` reports no difference), because the only commit between
the two revisions changes `.github/workflows/`.

```sh
git clone --local ~/Developer/x87sidecar /tmp/x87-scratch
cd /tmp/x87-scratch && git checkout 12afdc2
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j 2
./build/bin/x87sidecar --probe   # expect "supported"
```

Recipes now declare the staged artifact
`{games}/rebuild-bundles/sidecar-20261002-12afdc2/x87sidecar`, which is the binary the pin
describes, kept beside its `provenance.txt`. A developer with a built tree can point at it
instead with `--input sidecar=~/Developer/x87sidecar/build/bin/x87sidecar`; any path works as long
as the file's SHA-256 is the pinned one.

## 8. What the user has to do

1. **Install the EA app** into the same Windows prefix as the game, from `ea.com`. The app will
   not start the game without it and says so.
2. **Sign in,** in EA's own UI. The app never stores, replaces or works around the sign-in, and
   it checks only that an account folder exists — it never reads its contents.
3. **Expect to activate the machine.** EA's "Activate Your Game" dialog reappears when the Wine
   build changes, because activation is machine-bound. **[verified]** — it happened here. This
   needs the user's own sign-in and cannot be automated.
4. **Choose the Windows folder** in the starter, once. Nothing is copied out of it.
5. **For a Sony controller,** press *Enable Controller Support* once. It is a separate button, not
   part of launching, because it writes one key into a prefix the app does not own.
6. **Starting a session:** the EA app opens first and must finish signing in; the app then asks it
   to launch the game. Quitting the EA app ends the session.

## 9. Known risks and limitations

**The protection fix is a workaround with a real cost.** Trap-flag emulation single-steps while a
breakpoint is armed. The author's own caveat: *"Even ported, I expect TF emulation to be slow
enough that the protection's own timing checks may fail."* It has not failed in the runs made so
far, but it is the most likely source of a future intermittent failure, and a timing-sensitive
protection check is exactly the kind of thing that passes on one machine and fails on another.

**The durable fix is a real ARM64 hardware breakpoint** at the Rosetta-translated address. The
`ARM_DEBUG_STATE64` path is defined in Wine's protocol and has **zero implementation on either
side**: `server/mach.c`'s get/set bodies are `#if`'d to x86 only, and `signal_arm64.c` carries a
`FIXME`. **[verified]** Doing it needs a guest-PC to host-PC map plus translation-invalidation
handling; the only existing code here that does that mapping is
`x87sidecar/rosetta_loader/src/guest_pc_map.cpp`.

**Machine-bound activation** will recur on any runtime change. Not a defect, but it will surprise
a user who updates the app.

**Toolchain parity** — §4. The shipped PE builtins came from a different compiler than CI uses.

**A separate, still-open Wine bug:** the 32-bit wined3d/DXGI/D3D10 path faults reading
`0x00005dc9` at `ntdll+0x1123d`. It is worked around per application by disabling `IGOProxy32`,
**not fixed**. **[verified]** Anything else that uses 32-bit DXGI in this runtime will hit it.

**Verification bounds.** Gameplay beyond the controller-layout screen is not verified here. No
frame-rate or sustained-play measurement was taken. The EA client's behaviour on any backend
other than D3DMetal is unmeasured. Several large logs in this tree were only pattern-matched, not
read in full, so absence of a symptom in them is not proof of absence.

## 10. Rebuilding the runtime

See [`Packaging/NFS2015Runtime/BUILD.md`](../Packaging/NFS2015Runtime/BUILD.md) for the base
commit, `git am` procedure, configure flags and third-party pins. The short version:

```sh
git clone https://github.com/athei/wine wine-src && cd wine-src
git checkout 1a7b0c76
git am /path/to/Packaging/NFS2015Runtime/patches/*.patch
# then configure with the flags in BUILD.md, using llvm-mingw for the PE side
```

The packager will refuse a runtime that does not carry the gate or the selected backends: before
staging, it requires every selected renderer backend to exist as a real directory in the runtime,
and requires `WINE_TF_EMULATION`, `WINE_TF_MAX_STEPS` and `WINE_TF_MAX_NS` to be present in the
built `lib/wine/x86_64-unix/ntdll.so`. Those checks exist because **two renderer reversals on this
project were both caused by naming a backend the runtime did not contain.** A declared capability
is only a claim; measure it.

| Gate | Where | Refuses |

### 13.4 What the app does on first launch

The first launch is one operation, `--prepare`, run by the session helper under the session lock.
It needs Rosetta and does the following, in order, in a staging folder, and publishes everything
only when all of it succeeded:

1. Creates a **fresh private Windows prefix** with `wineboot --init` from the app's own patched CX
   11.0 runtime. It never copies, reads or looks at any other prefix.
2. Records the recipe's registry values: `RetinaMode=Y` (§3.4), the EA installer's own
   registration of the game under `HKLM\Software\Wow6432Node\EA Games\Need for Speed`
   (`Install Dir`, `Locale`, `Product GUID`, the three non-personal values the installer wrote), and the
   `Hidraw=0` controller keys for the DualShock 4 and DualSense (§3.5).
3. Copies the packaged game into `C:\Program Files\EA Games\Need for Speed` of that prefix,
   file by file, verifying each against its manifest hash. On the same APFS volume this is a clone
   and costs almost no disk; across volumes it needs the whole 14.6 GB and the app checks first.
4. Publishes the prefix and a `seed.json` record as one atomic rename. An interrupted first
   launch leaves nothing behind and starts clean the next time.

**Press Install EA App** later does one more thing first: it installs the pinned Wine Mono
(`Contents/Resources/Addons/wine-mono-10.4.1-x86.msi`, verified against its SHA-256 before it runs)
into the prefix with `msiexec /i … /qn`, unless the prefix already holds it, and from then on
every Wine process in that prefix runs with `mscoree` enabled (§13.9). A prefix made by an earlier
build is fixed the same way, because the check is on the prefix, not on the version.

The runtime switches (`WINE_TF_EMULATION=1`, `WINE_TF_MAX_STEPS=0`, `WINE_TF_MAX_NS=0`), the
`WINE_COMPATDB` rules that serve `NFS16.exe` and `EADesktop.exe` with dxmt, and the
`IGOProxy32.exe`/`winemenubuilder.exe` overrides are applied to every Wine process the app starts,
exactly as in the Import edition. After that first launch the game folder belongs to the player's
prefix and to the EA app, which patches it in place; **an app update never replaces it** and never
resets the prefix.

### 13.9 The EA installer failure of 2026-10-02, and what fixed it

**Symptom.** `Install EA App` ended with "The EA app was not installed (the installer ended with
status 1)". The session log held only Wine's `compatdb:` lines; EA's own log, written inside the
prefix at `drive_c/users/crossover/AppData/Local/Temp/EA_app_<timestamp>.log`, held the cause.

**Evidence chain.**

1. EA's installer is a WiX Burn bootstrapper. Its UI worked, it downloaded the 246 MB MSI (so
   network, TLS and WinHTTP were fine) and verified it. Then `Applying execute package …` ended
   after four seconds with `Error 0x80070643: Failed to install MSI package` (MSI 1603) and
   `Exit code: 0x1`. Nothing else in the log is an error.
2. Reproduced headless on a private clone of the app's runtime and a fresh private prefix, with the
   app's exact environment (`EAappInstaller.exe /quiet /norestart /log …`, the same options a
   successful install on 2026-09-26 used): the same 0x80070643. With `WINEDEBUG=+msi`:
   `err:msi:ITERATE_Actions Execution halted, action "JunoInitializeSession" returned 1603`.
3. `JunoInitializeSession` is a **managed** custom action: its binary stream is a WiX DTF `SfxCA.dll`
   that imports `CorBindToRuntimeEx` and carries `Microsoft.Deployment.WindowsInstaller.dll`. It needs
   a .NET runtime. The prefix had none (Wine Mono is not shipped with the runtime and `wineboot` does
   not install it), and the app also set `WINEDLLOVERRIDES=…;mscoree,mshtml=`, which disables `mscoree`.
   With `mscoree` enabled and no Mono, `+mscoree` shows `CLRRuntimeInfo_GetRuntimeDirectory error
   reading registry key for installroot`.
4. The 2×2 experiment, one variable at a time, same prefix recipe and installer:

   | Wine Mono in prefix | `mscoree` | Result |
   |---|---|---|
   | no | disabled (the app) | 1603 |
   | no | enabled | 1603 |
   | yes | disabled | 1603 |
   | yes | enabled (`mshtml` still disabled) | **installs, exit 0** |

   The working prefix of the earlier debugging has `C:\windows\mono\mono-2.0` and no override,
   which is why the same installer succeeded there.

**Second defect, found by the first fix.** With the install working, EA's window never appeared.
`EACefSubProcess.exe` (the Chromium helpers: network service, renderer) failed on every start with
`err:module:import_dll Library dxgi.dll (which is needed by libcef.dll) not found`, status
`c0000135`, and EA logged `Network service crashed, restarting service` in a loop. The recipe served
only `NFS16.exe` and `EADesktop.exe` with dxmt; every other executable resolved to the `gptk`
backend, whose folder this bundle deliberately does not ship, leaving only a 1.5 KB stub
`dxgi.dll`. The development runtime still had `gptk`, which is why this never showed there. Adding
`EACefSubProcess.exe` to the renderer rules removed the crash loop and the not-found error
(measured). **The Import edition shares this recipe, so its EA client had the same fault.**

**Fix.** (a) The recipe declares `managedRuntime` (Wine Mono 10.4.1, SHA-256 `071f4b28…e358e23`,
identical to the file WineHQ serves at `dl.winehq.org/wine/wine-mono/10.4.1/`, and the exact version
this Wine's `appwiz.cpl` asks for). The packager stages it under `Addons/`, with a notice. (b) The
session installs it before EA's installer (hash-checked first; idempotent) and enables `mscoree`
only for a prefix that really holds it, so a prefix without Mono never raises Wine's install prompt
and the Import edition's environment is unchanged by it. (c) `EACefSubProcess.exe` is served with dxmt.
Gates: `check_nfs2015_recipe.py` (both rules, mutations), `check_bundle_hygiene.py` §5 and
`audit.py` (pinned installer, nothing beside it, none in an import app), and the Swift tests in
`ManagedRuntimeTests`.

**Not changed, and why.** EA's installer still runs with its normal window; nothing passes
`/quiet`. The EA app's own self-update runs the same MSI, so it needs `mscoree` too; that is why the
override follows the prefix instead of applying to the installer step only. That an in-app update
completes is not verified.

**Verified in the built app (2026-10-02).** `Need for Speed Bundled 20261002-d5fc324-ea-fix.app`

### 13.11 The second real run (15:25 to 15:28): Play waited on the wrong evidence and then tore EA down

The `setup-fix` build failed with "The EA app did not finish starting within 180 seconds" while EA
was running and healthy: its start line, `login` and `client.boot.ready` were all in its log 19 s
after Play, and `EADesktopVerbose.log` kept growing until the session was torn down.

**Why.** Two defects, one found by experiment each.
1. The wait watched `cef.log`'s modification time through one `URL` it reused every second. A `URL`
   caches the resource values of its first read, so the wait kept seeing the time from before the
   client started (probe: write, read, write, read again on the same `URL` returns the first time; a
   new `URL` returns the new one). The unit tests read it once, on a new `URL`, so they passed.
   The fault is older than this change: the original folder-time rule read through a reused `URL` too.
2. On a timeout the session ended the client and stopped Wine, so a healthy client was killed for
   a failure of the wait itself.

**What changed.** Readiness is the client's own events (`NFS2015-RECIPE.md`, Readiness), the client
is never ended while it is alive, and the next Play reuses it. Play enables on the same rule as
before (the EA app installed, its profile folder present); when the client is up but not ready the
starter shows what to do and Play stays pressable.
Found only by running the new rule on the real log (read in place, nothing copied or printed but the
verdict): the log ends its lines with CRLF, which Swift reads as one character, so the first version
took the stamp of the first line of the window; fixed, with a test using CRLF lines.
On the real log of that run the rule gives *ready* for a client started at 15:25:49 (it was ready at
15:26:08) and *not started* for a client started after the last start line.

**Not verified**: a signed-out client (no run of that state is in the logs but the first, where
`login` first appears after the credentials were typed); that EA's launch request starts the game from
this state; a client that is wedged (Play reports it and leaves it; quit it from its own window).

### 14.1 How it is built, and why it does not depend on any prefix

- **The payload is a standalone copy, not a working prefix.** `Packaging/Recipes/nfs2015.json` names
  `{games}/NFS2015-game` as its `game` input. That folder is an APFS clone of exactly the 144 files the recipe
  lists (14,639,595,955 bytes), made from the verified installation by `tools/make-nfs2015-game.py`: it
  clones only the listed files, so the `NFS16.dxvk-cache` that sat beside the game, and anything else a used
  prefix accumulates, is not in it. File modes and times are kept as in the install, because the app clones
  them into the player's prefix and EA's updater must be able to write there; only the folders are made
  read-only. The packager still checks the pinned executables, the inventory digest (`353caa50…2a95`) and the
  account-state scan before it copies a byte, so the build fails if one byte differs from the verified install.
  A new check refuses a recipe whose `game` input looks like a Windows prefix.
- **Nothing of the build Mac ships.** The Swift binaries had the linker's debug map, which lists the absolute
  path of every object file (the account name, the checkout and the build folder); it is now stripped. The
  recipe an app embeds, and the recipes inside `launcher-source.tar.gz`, carry `build input, not shipped`
  where the input folders were. That archive holds the tracked source only: it used to include
  `__pycache__`, whose bytecode records the absolute path of each source file. The audit now fails if any file of
  ours, or any member of a source archive, names the build Mac's home folder.
- **Provenance is not borrowed from another game.** The app used to record the Most Wanted base app's mtld3d
  revision (`2513602…`), ship that revision's source archive and claim a renderer test result. It now records
  `sourcesNotApplicable.mtld3d` and carries neither. See `UPSTREAMS.md` for what the runtime still holds.
- x87sidecar `c396937` (`160e06be…bae5`) is the same pin as before. This app loads no mtld3d renderer of its
  own: `NFS16.exe` and the EA client are Direct3D 11 programs served by dxmt.

### 14.3 Moving the app: Gatekeeper, and what will not work

- **The app is Developer ID signed and not notarized.** `spctl` reports `rejected, source=Unnotarized Developer
  ID`. On the Mac that built it that is harmless, because a file copied there has no quarantine mark. **On
  another Mac, Gatekeeper will block it once it has been transferred**: AirDrop, a browser or mail download, a
  zip extracted by Archive Utility and many cloud downloads usually set the `com.apple.quarantine` attribute, and an
  unnotarized app with that attribute is refused with a message that Apple could not verify it.
- To open it, in this order of preference, and only after checking where the app came from:
  1. Try to open it once, then open **System Settings > Privacy & Security**, scroll to Security, and press
     **Open Anyway** for this app. (On macOS 15 and later, Control-click > Open no longer bypasses this for an
     unnotarized app; on macOS 14 and earlier it does.)
  2. Or remove the mark yourself: `xattr -dr com.apple.quarantine "/path/to/Need for Speed Bundled ….app"`.
  A copy made on the same Mac, or over a local drive that does not set the attribute, needs neither.
- **Not carried by the app, so the second Mac starts clean:** the EA sign-in, the EA app, the machine
  activation, the game's options and the saves. They live in that Mac's own `~/Library/Application Support/NFS2015Mac`;
  moving the app never moves them, by design.
- **Will not work:** an Intel Mac; macOS 14 or earlier; a Mac without Rosetta; starting the game without the EA
  app signed in to an account that owns it (the game is a hard dependency on the client, §3.1). The app is not
  notarized, and notarizing it is a separate step that has not been taken.
- **Not known to work:** any game feature that needs EA's online services beyond the sign-in, controllers other
  than the two Sony pads the app configures, and gameplay beyond what §9 records.

## 15. The complete portable app: the EA client comes with it

`Need for Speed Bundled <date>-<mtld3d>-portable-complete.app` is the portable app of §14 with EA's own client
inside it, so that on another Apple-silicon Mac a player **opens the app, waits, signs in with their own EA

that has been started once; it still needs the player's own EA account, EA's one-time activation prompt, the

> **This app contains the user's own licensed game files and EA's own client programs, for the user's personal
> use on their own Macs. It must not be redistributed.** It contains no EA account, session, token, cookie,
> machine identifier, activation record or credential, and no save. The player signs in themselves (§15.8).

### 15.1 What the player does

| Step | Before (§13, §14) | Now |
|---|---|---|

### 15.2 How the client gets in: a pre-installed, never-signed-in layer

At **build time** `tools/capture-client-layer.py` makes the *client layer*:

1. It verifies that the installer is Authenticode-signed by `Electronic Arts, Inc.` (`Packaging/authenticode.py`:
   the PE digest, the signed attributes, the signature, the chain to DigiCert Trusted Root G4 in the macOS root
   store, the code-signing usage) and records its SHA-256.
2. It makes a pristine prefix with a built app's own `--prepare` (Wine's defaults, the recipe's registry
   values, the dxmt rules' environment, the game copy) with Wine Mono installed first, and snapshots every file
   and both hives as the baseline.
3. It downloads the installer's MSI with the installer's own `/layout` in a clone of that prefix (the only use of
   the network; the clone is deleted) and records the MSI's SHA-256.
4. It runs the installer `/quiet` in the pristine prefix under a macOS sandbox that **denies every IP
   connection**, so the client can never reach EA's sign-in, and ends the Windows side the moment the installer
   exits; a client process that appears is killed at once. Nothing is typed and no window is opened.
5. It diffs the prefix against the baseline and classifies **every** added or changed file and registry key with
   the rules of §15.3. A path no rule names stops the run, so a newer installer is reviewed by a person.
6. It writes the layer and runs the gates of §15.4.

The layer is the folder `inputs/client-layer`, pinned in `Packaging/Recipes/nfs2015.json` by one digest: the SHA-256
of its manifest, which names every file by size and SHA-256 and every registry part by SHA-256.

| Pin | Value |
|---|---|
| Installer | `EAappInstaller.exe`, 2,141,240 bytes, SHA-256 `dcbda653…9320` (the installer of §EA-APP.md), signed `Electronic Arts, Inc.` by DigiCert Trusted G4 Code Signing RSA4096 SHA384 2021 CA1 (certificate valid 2026-05-11 to 2027-05-10; the signature carries an RFC 3161 timestamp of 2026-09-24, which is reported and not verified) |
| Package | `EAapp-13.796.0.6309-15736974.msi`, 246,083,584 bytes, SHA-256 `cb773af8…cdc8`, the version the installer fetched on 2026-10-03 |
| Layer | 971 entries (906 files, 65 folders), 1,092,247,235 bytes installed, 846,157,982 bytes stored, 947 keys in `system.reg` and 1 in `user.reg`; digest `9ed3bf73…6f86` |

Inside the app: `Contents/Resources/ClientLayer/` (the manifest, `blobs/<sha256>`, `registry/*.part`),
`Licenses/ea-client.txt`, a `clientLayer` entry in `game-manifest.json` (so it is part of the signed bundle and of
the manifest version), and a `clientLayer` entry in `runtime-provenance.json`.

At **first start** the session helper's `--prepare` builds the new prefix in a staging folder and publishes it by
one atomic rename, in this order: `wineboot --init`; the recipe's registry values; the controller keys; **Wine
Mono** (`msiexec`, hash-checked, as before); then, with Wine stopped, **the client layer**
(`LauncherCore/ClientLayer.swift`): every file is an APFS clone of the layer's blob (a copy across volumes), hashed
against the manifest; the allowed extended attributes are set; then each registry part is appended to the stopped
prefix's hive file. The hives are edited as text because Wine's own format keeps every value type byte for byte,
which a `reg import` of the same data cannot promise. Anything wrong (a blob that differs, a link where a folder
should be, a registry key the prefix already has) stops the first start and leaves nothing published.

### 15.3 What is kept, what was removed, and how that was decided

The layer is **allow-listed**: a path or key is kept only when a rule below says so. Each decision was made by
reading what the installer wrote, not by guessing; two independent installs were compared, and everything that
differs between them is per-install state. The rules live in `Packaging/client_layer.py` (`FILE_RULES`,
`KEY_RULES`) and this table is generated from them (`client_layer.py describe`); `check_client_layer.py` fails
when a rule has no row here. `drop` is deliberate removal, `forbid` stops a build.

- `machine.ini` holds random experiment and update buckets, telemetry statistics and the EA update/telemetry
  settings; the identifier folder under `ProgramData/EA Desktop` is named by a 64-digit hexadecimal value and holds a
  128-digit token (`IQ`); `backgroundservice.ini` holds the service's process id. All are written by
  `EABackgroundService`, which the installer starts, and are recreated by the client on the player's Mac.
- `state.rsm`, the setup engine's resume state, contains the build Mac's account path (as UTF-16): it is the one
  kept-looking file that is *not* identical across machines, and it is dropped.
- The prefix's hives hold, from Wine itself and not from EA, the host keychain's root certificates
  (`HostImportedCertificates`), the host's controllers with their Bluetooth addresses and fresh container
  identifiers (`Enum`), and the build Mac's home path; none is in the layer, and the baseline hives are never shipped.
- Three keys appear in some captures and not in others (WinINet/WinHTTP `SecureProtocols` and the Schannel TLS 1.2 client
  switches, rules R13 and R14): the values were examined (a bit mask and two flags, no identifier) and the keys are dropped,
  because a key that a run may or may not write would make two captures differ.
- `EACore_App.ini` is the only `.ini` in the client; it is a static agent table with placeholders (`{clientGUID}`),
  identical in both installs, and is kept by name.
- Both installs produced the same 902 client program files byte for byte; the only files that differed were
  shortcuts (`.lnk`, which embed the install time), temp files, logs, `machine.ini`, `backgroundservice.ini`,
  the telemetry cache and Windows Installer's randomly named cached MSI.
- The client itself never ran during capture: the installer exits 0 under the no-network sandbox, no `EADesktop.exe`
  process was seen, no `EADesktop.log` exists, and there is no `AppData\Local\Electronic Arts\EA Desktop\Logs`. The
  installer's last step starts `EALauncher.exe`, a stub, for the two seconds before the installer exits; the
  background service runs during the installation, which is where `machine.ini` came from.
- The task named the services `EABackgroundService` and `EALocalHostSvc`. This client version (13.796.0.6309)
  registers only `EABackgroundService`; there is no `EALocalHostSvc` key in the install, so none is in the layer.

**Normalized so that two installs are byte-identical:** Windows Installer's cache name (`6417.msi`, `ed43.msi`, …
random) becomes `windows/Installer/eaapp.msi` and the registry value that names it follows; `InstallDate` becomes
`20260101`; every key's timestamp becomes 2026-01-01 00:00 UTC; file modes become 0644 or 0755; the MSI that Windows Installer
caches twice is stored once. `com.apple.provenance` (macOS bookkeeping of the build Mac) is never carried; Wine's
`user.WINEREPARSE` (the `EA Desktop` junction) and `user.DOSATTRIB` are.

### 15.4 The gates

- `Packaging/check_client_layer.py`: classification (state is never kept), unreviewed items stop the build, two
  installs with different random names, dates and machine values give **the same layer digest and the same bytes**,
  fourteen tampering mutations are each refused, the reference apply reproduces every kept file, attribute and
  registry key, the registry merge, and a shared path-policy fixture that the Swift tests run against the app's own
  policy. The capture tool's own gates: the cached packages equal the pinned installer and MSI; no identifier of the
  build Mac or of the captured machine state (home path, host name, Bluetooth address, machine identifiers,
  the IQ token, every long hexadecimal value and GUID of `ProgramData/EA Desktop`) occurs in any kept byte, raw or
  UTF-16; the layer applied to a clone of the baseline equals the install.
- **Reproducibility, measured:** four captures, each with its own scratch prefix and scratch folder (the last one with
  the final tool and policy), gave the layer digest `9ed3bf73…6f86`, and `diff -r` found the first two folders identical.
- The packager (`assemble.stage_client_layer`) refuses a layer that does not match the recipe's pin or policy before
  it clones one byte; `audit.py` (`audit_client_layer`) re-checks the finished app and refuses a layer in any app
  whose recipe has none; `ClientLayerPolicy.swift` refuses the same paths again on the player's Mac, whatever a
  manifest says. The Swift tests (`ClientLayerTests`) apply the layer, tamper with it, and attack it with a link, a
  clashing key and 17 malformed manifests.

### 15.5 First-start cost: clones and verification

The game files and the layer are cloned (`clonefileat`) when the app and the player's folder share an APFS volume,
and copied otherwise. **Every file is still hashed after it is placed**, clone or copy: the hash of a clone is a read
of the app's own bytes, so it proves the app was not damaged in a transfer, and it is the same gate for a copy
across volumes. Skipping it on a clone would weaken the integrity gate for nothing. `PrefixSeed` checks the free space
first (about 15 GB plus the layer across volumes; nothing on one volume) and shows the determinate bar of §14.4 for the game files.
An app that macOS runs from a temporary read-only copy (App Translocation, which happens to a downloaded app that was
not moved or approved) cannot be cloned from; the starter says so (`NFS2015FirstRunGuide`) and the first start copies.

Measured on the Mac that built it (Apple silicon laptop, internal SSD, other jobs running): `--prepare` (wineboot,
Wine Mono, the client layer, 144 game files cloned and hashed) took 68, 101, 112 and 114 s in four first starts, two of them
under the read ban with every IP connection denied; a second `--prepare` took 0.6 and 0.8 s and started nothing.
**Across volumes:** the real layer (906 files, 1.09 GB) was applied by the app's own Swift code from the app's APFS volume
to an HFS+ disk image, which cannot clone: every file went through the hashing copy and was verified again afterwards, and
the junction attribute was set. The game files use `VerifiedGameFile`'s existing fallback, which is unit-tested; a full
14.6 GB cross-volume first start was not run.

### 15.6 The client's own first start

The client that is installed is `13.796.0.6309`. EA's client updates itself; this app does not stop it, and

### 15.7 Distribution: Gatekeeper, honestly

The app is Developer ID signed and **not notarized**. After AirDrop, a browser or mail download, an unzip or most cloud downloads,
macOS marks the app as quarantined and Gatekeeper refuses to open an unnotarized app until the player decides.
The decision is theirs: only after checking where the app came from, either use System Settings > Privacy & Security >
**Open Anyway** after one failed open, or run `xattr -dr com.apple.quarantine "<the app>"` in Terminal (type that
command, a space, drag the app into the Terminal window, press Return). On macOS 15 and later Control-click > Open
no longer bypasses Gatekeeper for an unnotarized app. A copy made on the same Mac, or by a drive that does not set the
mark, needs nothing. Moving the app to the Applications folder, or removing the mark, also avoids translocation (§15.5).
The delivery is **the app plus a plain text file beside it** (`docs/OPEN-THIS-FIRST.txt`, delivered as `Open This First - Need for Speed portable-complete.txt`): no zip, no checksum file, no disk image. A disk
image would cost another 16 GB of free disk and, downloaded, would carry the same mark. It needs Apple silicon, macOS 15
or later, Rosetta 2 (the starter installs it), about 40 GB free during the first start, and it is for personal use only.

## 16. The settings page

### 16.1 What it edits, and what it never touches

The page reads and writes `Documents/Need For Speed/settings/PROFILEOPTIONS_profile` below the

was found at `~/Documents/Need For Speed/settings/PROFILEOPTIONS_profile`, so the prefix's `Documents` is

The app keeps no copy of the values: the file is the only record, so a change made in the game's own

bytes, ASCII, line feeds, every line `Key Value` with one space and a numeric value, no blank line, no
repeated key, every key in a `Gst` family. 48 lines are options (`GstRender`, `GstInput`, `GstAudio`)
and 328 are `GstKeyBinding` lines, which the app preserves and never edits. No value from that file
is in this repository; the tests use invented files of the same shape.

It never touches:

  `-GameTime.MaxVariableFps` are reported for another title). The page has a disabled **Launch

### 16.3 How a change is made

The page sends the helper only the settings the player changed, plus the SHA-256 of the file the
player was looking at. The helper (under its session lock and game lease) then:

1. replays any interrupted edit, then refuses unless the game is not running. The check looks for
   `NFS16.exe` in the process list, so a game started by hand through the EA app counts, and an
   answer it cannot get counts as running;
2. refuses unless the file's bytes still have the fingerprint the player saw. The file is checked
   again immediately before the write, because the game rewrites it at exit;
3. refuses unless the file has the validated layout (above). A repeated key, a blank line, a text
   value, a stray byte, a key outside the `Gst` families, a lone carriage return or an unexpected
   size is refused whole, and the page then shows the file and offers nothing to write;
4. refuses a value outside its range, an unknown setting, or a key the game has not written;
5. keeps the backups (§16.4), replaces the file atomically, reads it back, and requires the bytes
   to be exactly what was planned. If not, the earlier bytes are put back and the page says so;
6. reports the lines that changed as the file now holds them.

Only lines whose value differs are written, so a line the player did not touch keeps the exact
digits the game wrote. Every other line, the line order, each line's own ending (line feed or
carriage return plus line feed, even mixed) and the presence or absence of a final newline are
preserved byte for byte. Before the game has written its file the page says so and offers nothing.

### 16.4 Backups and recovery

Two copies are kept in the app's own support folder, `Backups/`, and only of files that passed the
layout check:

- `PROFILEOPTIONS_profile.original`: the file exactly as it was before the app first changed it.
  Written once, never replaced.
- `PROFILEOPTIONS_profile.previous`: the file as it was before the latest change, replaced each time.

**Restore Game Defaults** puts back `.original`; **Undo Last Save** puts back `.previous`. Both obey
every rule in §16.3, so they refuse while the game runs, and a restore keeps the current file as
the new `.previous`, which makes it undoable too. "Game defaults" means the file as the game had
written it before the app's first save. It is not a factory reset, and it drops any change made in the
game's own menus since.

If the page refuses and shows a message you cannot act on: quit the game and the EA app, then copy
`~/Library/Application Support/NFS2015Mac/Backups/PROFILEOPTIONS_profile.original` over the options
file at the path in §16.1. Never edit or delete the binary `PROFILEOPTIONS` file. Deleting the text file
so the game rewrites it **has not been tried** and is not part of the recovery. A write interrupted
by a crash is rolled back at the next session start from `player-file-edit.json`.

### 16.5 Mac-specific notes (also in the page)

- The app sets Wine's `RetinaMode` (§3.4), so the game sees the panel's native size, such as 2560 by 1600.
  Resolution and refresh rate in the file are what the game asks for. MetalFX is a separate group on the page and is not a game option (§17).
- Vertical sync may hold the frame rate at 60 on a ProMotion display **[inferred]**; the page says so
  rather than offering a rate it cannot guarantee.

None of these is known. Each needs a player with the game, one change at a time:

### 17.2 What the app offers, and what the settings mean

The settings page has a **MetalFX** group, separate from the game's options because it is not one:
it is stored in `metalfx.json` in the app's own support folder, never in the game's files, and it
works before the game has written its options file.

- **Upscale with MetalFX (spatial)**: off by default. Off emits nothing at all.
- **Scale factor**: 1.25, 1.33, 1.5, 1.75 or 2.0, all inside DXMT's documented range. The app starts
  at 1.5; DXMT's own default is 2.0. `1.33` is DXMT's own example (1080p becomes about 1440p).
- There is no quality setting because DXMT has none, and no temporal or frame generation switch (§17.4).
- **Save MetalFX**, **Discard** and **Reset MetalFX** (removes the file, which means off). A file that is
  missing, oversized, not valid JSON, of another version or holding any other factor is treated
  as off and the page says why; it never stops the game starting.
- **Both editions.** The group is part of the starter, so the Bundled and the Import app of the merged
  line (§18) offer it alike, with the same defaults (off). Its file is in the app's own support folder, so
  the Import app writes nothing into the player's Windows folder for it, and the choice reaches
  `NFS16.exe` through the same per-program rule in either edition.

The file holds `{"factor": "1.5", "spatialUpscaling": true, "version": 1}` and is replaced atomically
and read back. A save is refused while the game or the EA app started by this app is running
(the same lease as the game's settings), and takes effect the next time the EA app is started by
Play, because the game inherits what the EA app was started with.

**What it hands to DXMT.** When on, the launch gives the game's executable, and only it, these
variables: `DXMT_METALFX_SPATIAL_SWAPCHAIN=1` and
`DXMT_CONFIG=d3d11.metalSpatialUpscaleFactor=1.5`. They travel as `env=` fields of the game's
`WINE_COMPATDB` rule (`NFS16.exe`), which the runtime applies to a process only when its image
name matches; the EA app, its browser helpers and every Wine service get nothing, which the run in
§17.5 shows. They are not placed in the launch environment, which every Windows process of the prefix
inherits; `Packaging/check_nfs2015_metalfx.py` fails the build if any source does that, names any
other DXMT variable or option, or reaches the NVIDIA extension, a temporal scaler, frame generation
or MetalFX directly. Values cannot contain `;` or `%`, so a value cannot start another rule.

**Render resolution, scale factor and output**, from DXMT's code. The game keeps drawing into the
swap chain it created, at the size it chose; the game is not told anything else, so its resolution,
viewport, HUD layout and mouse coordinates are unchanged. DXMT then runs the finished picture,
HUD included, through the MetalFX spatial scaler into a second texture whose sides are the game's
multiplied by the factor (single precision, fraction dropped), sets the Metal layer's drawable to
that size, and presents it. The window does not change size. So the factor never lowers what the
game renders; it only enlarges what is presented. The page shows this arithmetic at the game's
current resolution and warns when the result is larger than the main display's pixel size.

On this Mac the game runs with Wine's `RetinaMode` (§3.4) at the display's native size, such as
2560x1600 (the 3360x2100 sizes seen earlier are the larger "More Space" modes that Retina mode
also lists). At the native size a factor of 1.5 presents 3840x2400 to a panel of 2560x1600: the
surface is made larger and then shrunk again by the system. **That is inferred from the code and
the arithmetic, not observed in the game, and it means the setting can cost GPU time without adding
detail unless the game runs below what the display shows.** If the game offers a lower resolution,
the useful pairing is the one that lands near the panel: 1280x800 with 2.0, or 1920x1200 with 1.33
(2553x1596).

### 17.3 Performance expectations

None is measured. MetalFX spatial scaling adds one GPU pass per frame on a surface of the presented
size, so it adds work that grows with the factor and does not reduce the game's own rendering cost,
because the game still renders at its own size. Whether that is paid back by running the game at a
lower resolution, and by how much, is a result for this Mac and this game. The smoke run in §17.5
is a one-colour test program; its frame rates say nothing about the game and are not quoted.

### 17.4 What is not offered, and why

- **Temporal upscaling.** DXMT implements it, but only as the target of NVIDIA's DLSS interface: the
  game must load `nvngx.dll`, create a DLSS feature and pass colour, depth, motion vectors, exposure
  and the camera jitter it used, which DXMT forwards to `MTLFXTemporalScaler`. Direct3D 11 itself
  carries none of those, so a translation layer cannot invent them. The game's own temporal
  anti-aliasing has motion vectors and jitter internally, but they are private to the game and not
  reachable through the API. This 2015 game predates DLSS and was not built to call it. Enabling
  `DXMT_ENABLE_NVEXT` would therefore change nothing for it, and could make other software think
  an NVIDIA GPU is present, so it is not offered. Making the game feed MetalFX would mean modifying
  the game or its protection, which this project does not do.
- **Frame generation.** DXMT v0.80 has no frame interpolator, and Apple's own needs the same
  depth and motion inputs. Not available.
- **MetalFX denoise.** Not in DXMT v0.80, and the game has no ray-traced signal to denoise.
- **A frame-rate cap** (`d3d11.preferredMaxFrameRate`) and the **DXMT HUD** are real DXMT options but
  are not MetalFX and are unmeasured here; they are left for a later change.

### 17.5 The run that was made

One short run, with the app's own runtime from the delivered portable app, a private Windows folder
created under `/tmp`, no game, no EA app, and the user's own folders untouched. The program is a copy
of `tools/ea-app/Diagnostics/d3d11-smoke.c` (a 640x480 window, one clear colour, 420 presents, plus a
line printing the swap chain size the program sees), built outside the repository and named
`NFS16.exe` so that the game's own rule applies to it. The `WINE_COMPATDB` text came from this
repository's own code for the recipe's three renderer rules, once with MetalFX off and once at 1.5.
The Metal HUD was on, and each window was captured alone by its window id (the captures show only that
window). The two captures, the logs, the two rule texts and the program's source were kept outside the repository, in an `evidence` folder beside the clone this was built in.

| | MetalFX off | MetalFX on, 1.5 |
| --- | --- | --- |
| Rule for `NFS16.exe` logged by the runtime | no `env` line | `env = DXMT_METALFX_SPATIAL_SWAPCHAIN=1, DXMT_CONFIG=d3d11.metalSpatialUpscaleFactor=1.5` |
| Other Wine processes of the run (explorer, rpcss and so on) | no rule | no rule, no `env` line |

So the setting **reaches DXMT, applies to the one executable, and engages the MetalFX spatial path
with the size arithmetic of §17.2**. That is all it shows. It is a flat colour: it says nothing about
image quality, sharpness, the game's HUD, frame rate or artifacts, and it ran on an Apple M1 under macOS
27.2 only.

### 17.6 Not verified

- Anything in the real game: that it starts, renders, and survives a swap chain of this size with the
  scaler in the path. Its swap chain format and any multisampling are not known here, and DXMT's
  code asserts that the scaler could be created, so a format it cannot take would fail inside DXMT.
  Reset MetalFX (or turn it off and save) returns to the unchanged path.
- Whether a setting saved while the EA app is already running reaches the game: the app refuses to
  save then, so the player must quit the EA app first. That is by design but was not run.
- The page itself (the SwiftUI group) was not run; its model is tested.

### 17.7 What a player must test

Change one thing at a time, start the game from the app each time, and note:

1. **Does it start and reach the menus** with MetalFX on at 1.5? If not, press Reset MetalFX and report.
2. **Visual quality and HUD sharpness**: the menus, the speedometer and minimap, text. The scaler
   enlarges the HUD together with the scene, so its sharpness is the game's own plus the scaler's.
3. **Frame rate and smoothness** with it off and on, at the same game resolution, and then with a lower game
   resolution and a factor that lands near the panel size (§17.2).
4. **Artifacts**: shimmering, haloing, ghosting of fast cars, or colour shifts; also with the game's
   own anti-aliasing and brightness settings changed.
5. **Persistence**: quit everything, reopen the app, confirm the page shows the saved choice, play again.
6. Whether the picture is **sharper or softer** than the same game at its native size with MetalFX off.
7. Whether turning it off again with **Reset MetalFX** restores the previous look.

### 17.8 Tests and gates

Swift suites: the environment rules (a variable reaches one rule only and cannot start another),
the MetalFX values and file (defaults off, every offered factor, exact environment text, exact file
text, round trip, atomic replace, reset, every invalid file falling back to off with a notice), the
size arithmetic, the request and the page model. `check_nfs2015_metalfx.py` is the gate that the
settings can never emit anything but the documented options, and it was proven against synthetic
hazards. Sixteen breakages of the Swift code (the variable reaching every rule, emitting while off, a
`;` allowed in a value, a reserved prefix dropped, the version check removed, reset not removing,
size rounding, the larger-than-display comparison, an unsaved choice equal to the saved one, a
refusal clearing the player's choice, unchanged-save detection, the request requirement, the
no-renderer path, a save without a choice, and a wrong factor) were each caught by a named test,
and twelve breakages of the gate were each caught by it. Final run: 602 Swift tests (560 before
this work), the release build with warnings as errors, strict `swift-format` lint, and all 16
`Packaging/check_*.py` gates. Not covered by an automated test: the session helper's own wiring of
the MetalFX request, and the SwiftUI group (both thin; the page was not run).
